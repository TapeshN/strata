A capability check that tests for one specific tool and concludes the machine altogether lacks that capability is a common and expensive false negative. One command-line file-conversion tool being absent got written up as "this machine cannot do X" in a handoff and a change description — when a different library providing the same capability through a different interface (a language binding rather than a standalone command-line tool) was already installed, found in under a minute once actually checked. An absent binary is evidence about that one binary; it says nothing about the capability class it happens to belong to. The fix at source: before reporting any "X is not available" capability blocker, enumerate the plausible alternatives in that capability's class — competing command-line tools, competing libraries, competing language bindings — and only report the blocker if none of them are present. Handing back a blocker that was never actually a blocker costs the receiving person more than the minutes it would have taken to check properly.

A second lesson from the same stretch of work: asking whether a piece of work is actually live has to be answered by finding the real serving process, not by consulting a branch name or a worktree inventory. A long-running demo instance was found to be running from a checkout that lived entirely outside the normal worktree-tracking system — invisible to any tool that only enumerates registered worktrees, by construction — and it was running its own independent line of changes that had reached the same structural conclusion as a separate, concurrent line of work, both edited against the same underlying file, neither aware of the other. Nothing in the ordinary inventory check surfaced the collision; only tracing the operating-system process actually serving the live address back to its working directory did. The generalizable rule: any long-lived, out-of-band checkout that serves something real needs to be discoverable the same way a registered worktree is, and "is it live" is answered by finding the process, not by reading a status board.

A third, smaller lesson from the same review: a domain-specific term appearing verbatim in a client's own data is a term of art, not a word to interpret from surrounding context. A status label in an inventory was read as a plain-English description and paraphrased plausibly but incorrectly; the term in fact referred to a specific legal status under a real body of property law, carrying a materially different set of consequences for what could and could not be done with the asset while it held that status. Getting the read wrong there would have told a downstream reader that an asset was permanently unavailable when it was, in fact, recoverable. Any domain vocabulary that appears verbatim in a client's own source data and materially affects a downstream decision needs an actual citation to its source meaning before it is used in any onward description, not an inference from context.

The unifying frame across all three: whether something is true, done, or live is a verification trigger, not a status question to answer from memory or from a plausible-sounding inference — it gets answered by running something (a broader probe, a process lookup, a source lookup), not by reasoning about what is likely.
