**1. A merge conflict on a living, working-set document should resolve to the newer state, not a union of both sides.** Merging a long-lived branch produced a conflict in a document that tracks current status — one row per unit of work, representing where things stand right now. Resolving by keeping both sides of the conflict, the instinctively "safe" choice, silently produced two rows for the same unit of work, one marked complete and one marked still in progress, and a consistency check correctly caught the resulting contradiction. The general distinction: union-of-both-sides is the correct resolution for an append-only log, where every entry is permanent history and nothing is ever superseded. It is the wrong resolution for a working-set document, where a row represents current truth and an older row is meant to be replaced, not preserved alongside its replacement. Resolving a working-set conflict should keep whichever side reflects the newer state and drop the superseded one — the same "evict what's been superseded" principle such documents already apply to their own regular upkeep, just applied at merge time too.

**2. When a UI's rendering legitimately changes, ask which layer of the system actually carries the guarantee before re-pinning a broken test.** A change to how human-readable messages were generated broke several tests that had been asserting the presence of specific words inside that rendered text. Most of those were simple, honest re-pins: the underlying behavior hadn't changed, just its wording, so the assertion was updated to match the new text with a comment explaining why. One test, though, had been parsing structured information back out of that same rendered text to prove something more specific had happened — that test was moved to assert directly against the underlying data the message was generated from, rather than against the message's prose. A test that parses meaning out of human-facing text is really a test of the underlying data wearing a costume; when its assertion breaks on a wording change, that is the signal to relocate it to the actual data layer, not just to update the expected string.

**3. Running a cloud deployment CLI from inside a project subfolder can silently create a new, empty project named after that folder.** Some deploy CLIs infer which project they're targeting from the current directory rather than requiring it be stated explicitly, and running one from a temporary or side working copy — rather than the canonical project checkout — can register a brand-new project scoped to that copy's folder name. Left alone, it sits unused indefinitely, yet may still be provisioned with real environment configuration and the ability to trigger its own deployments. Any CLI tool that can infer identity from the current working directory should be invoked with that identity stated explicitly, and a periodic audit of what such a tool has actually registered is worth doing independently of remembering to name things correctly every time.
